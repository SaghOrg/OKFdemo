# Learnings

Forward-looking rules only. Build archaeology from generating this corpus moved
to `/_learnings/prototype.md` in step 13; it is history, not instruction.

- **S11 staleness has two mechanisms, and they are not interchangeable**: `stale_after` is *time-based* — nobody has reviewed this file recently, so distrust it as a whole. A body-level supersession note is *fact-based* — this specific claim is wrong, and here is where the current value lives. Only one file in the KB carries `stale_after` (`/context/active-context.md`, `2026-11-13`), which is correct: it is the file whose entire contents decay by the calendar. The note that actually caught a real error was the other kind, and it was written unprompted — the closing paragraph of `/context/project-brief.md`, stating that go-live moved twice, pointing at `/log.md` as authoritative, and naming the specific wrong value to distrust (`15-Sep-2026`, the date the brief's own source deck `DK-01` was written against). Nothing asked for that paragraph; a schema check would not have missed it, because nothing was missing. The general rule: put time-based flags on files that go stale as a whole (active context, status, anything narrating "now"), and put fact-level supersession notes wherever a specific claim was superseded — including inside otherwise-stable documents like a project brief, which does not go stale as a whole but can carry a single fossilised figure. A stable file is exactly where a stale fact hides best, because nothing about the file looks old.

- **S5 repair follow-up**: repairing links creates new one-directional edges. The backlink pass has to run *after* every link-editing change, not once — link symmetry is a property to re-establish, not a one-time fix.

- **S10 cross-linking, an unprompted schedule risk**: the most valuable thing the knowledge base produced was not an answer to a question anyone asked. Reviving the credit-note extract — the fix `VAR-005` has been open on since the start — reopens the exact load-window pressure that got `MAP_STG_CREDIT_NOTE` disabled on 14-Nov-2022, and that cost has never been measured. `ADR-004`'s key-based rebuild of `MAP_FACT_INVOICE_LINE` (`/decisions/20260506-var003-remediation-key-based-merge.md`) is a second unbuilt remediation contending for the same nightly window. Neither has been sized, both are pending against the 05:30 IST availability SLA, and both land twelve days before the 12-Nov-2026 go-live, against a schedule with almost no float. **No single source document contains that connection.** It exists only because a 2022 operational decision, an unbuilt 2026 remediation, an SLA figure and a go-live date are separate concepts that link to each other — retrieval that stops at the one document answering the question asked will never surface it. The lesson for how the KB is built: cross-links are not navigation convenience, they are the mechanism by which a risk nobody thought to ask about becomes visible.

- **S9 review**: an adversarial pass by a stronger model caught a systemic sourcing defect, a mislabelled constraint, an invented date, and a false backlink claim that schema validation alone reported as clean.

- **S4 decisions**: Read AGENTS.md, schemas/concept.schema.json, and _canon/BRIEF.md, then targeted-grepped _canon/BRIEF.md (ADR numbers, dashboard/go-live variance tables) plus primary sources: T-03/T-04/T-05/T-07/T-08 meeting transcripts, DOC-04 (dimension strategy, contains ADR-001 to ADR-005 verbatim in Appendix A), EM-041/EM-047/XL-03 (DIM_CUSTOMER SCD2 objection+measurement), EM-023 (dashboard cut), EM-068 (go-live slip to 30-Oct), DK-05/DK-06 (dashboard candidates and reinstatement), EM-072 (Feb duplicate load resolution chain). Key structural finding: the decision.md template's frontmatter (id, deciders, consulted, informed, affects, date) is NOT OKF-schema-conformant (schema has additionalProperties:false and none of those keys are declared) — resolved by using only OKF/local-extension frontmatter fields and moving deciders/consulted/informed into a body section under the H1, preserving the MADR body shape (Context/Decision drivers/Considered options/Decision outcome/Consequences/Evidence/Follow-ups) as instructed. Also discovered that the T-03 'parked' February-reload question (one of the two explicitly-named deferral cases) was in fact resolved by email on 02-Apr-2026, before the T-04 session it was deferred to — wrote both the draft/open-question record for the T-03 parking AND a separate accepted record for the actual 02-Apr resolution, linked via supersedes/superseded_by, rather than either inventing a resolution or suppressing the real one found in EM-072. Validated all 13 files' frontmatter against schemas/concept.schema.json using a local jsonschema script (via the repo's .venv-synth) after normalizing PyYAML's auto-parsed datetime objects back to strings for the check only — confirmed this datetime-vs-string quirk is purely a YAML-loader artifact of my ad hoc validator, since all prior-stage concept files (tables, variances) already use the identical unquoted `at: <iso8601>` style, so I kept mine consistent with that established convention rather than quoting it.

- **S12 an unfilled verification field is not a neutral default, it reads as a passed check**: two instances, and they fail from opposite directions. `_canon/pii_plant_register.csv` asserts that each planted value is "present exactly once and nowhere else" and carries a `verified` column recording that the QA phase confirmed it; the sweep in step 2c found 29 occurrences across five files outside the archives, so the assertion was already false at the moment it was certified — and the three QA reports doing the verifying were themselves the leak. The schema's own `verified` key is the same defect inverted: declared with required `by` and `at`, described as the place human review is recorded, and used by zero of 72 records, so the channel that exists to prove a human looked has never once been exercised. Nobody reads a verification field and asks whether it was filled; its presence is taken as evidence that the check happened, which is exactly why an affirmative-but-false one is worse than an absent one — a reader has to disprove it rather than notice a gap. The rule: a verification field is only worth having if something fails when it is absent or stale. If nothing breaks when it is empty, it is decoration that reads as assurance.

- **S13 realistic test data propagates because it is useful**: two of the defects in this build-out were planted fixture credentials copied into new files — a QA report quoting a password into a table cell to evidence that the plant was where the register said it was, and a parser docstring using the same password to illustrate that a `#` not preceded by whitespace does not open a comment. Neither was carelessness, and that is the point. The fixture was at hand and it was realistic, which is precisely the property it was created to have; an obviously fake string would have been less convincing as evidence and less illustrative as an example. That is the mechanism: a value good enough to test with is good enough to quote, and every quotation is a fresh copy sitting in a file nobody classified as holding secrets. It happened twice more while writing this up — a progress report describing the fix reproduced the value, and a test suite for the scanner tripped its own check. The rule: never use a real fixture value as an illustrative example, including inside a comment. Substitute something inert at the moment of writing. A later sweep can find the copies, but only after they exist.
